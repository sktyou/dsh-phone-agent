如何调用三种接入方式,任选一种

方式一:DSH 插件让大模型直接调用(推荐)

插件装在 DSH 的 web profile 里,工具名 **phone_lan**。模型自己会挑 action,你只需要用自然语言描述目标。

地址在插件包自己的 cordis.patch.yml 里配置(host / port / toolName),改完要重启 DSH——新增或改配置都不会热加载。

方式二:原始 TCP一行一个 JSON,任何语言都能接

不依赖任何 SDK。协议就是 **一行一个 JSON**,UTF-8,`\
` 分隔,默认端口 **7912**。

响应也是一行:成功是 `{"ok":true,"data":{...}}`,失败是 `{"ok":false,"error":"...","code":"..."}`。单条失败**不会断开连接**,可以继续发。

方式三:Python 客户端现成的参考实现

`pc/pyclient/phone_client.py`,约 200 行,直接读它就能理解协议。不需要的话可以在脚本里更简单地自己写一个。

频率与限流高频发送会怎样,以及正确的写法

服务端**串行执行**所有操作:同一时刻只处理一个,后到的排队。

所以**不要不等响应就连续发**。一次 tap 要「手势 + 截图」约 300–800ms,连发 100 个的话,第 100 个要等近一分钟才回,看起来就是卡死。

App 侧做了两道保护:

1. **点击节流**——两次点击之间强制最小间隔,默认 110ms(大致是人手最快连点速度)。可用 `minIntervalMs` 调整,设 0 关闭。
2. **并发上限**——同时有 4 个操作在跑时,新请求直接返回 `busy` 错误而不是排队。

**滑动和长按不受节流约束**:它们本身就是长动作,强行间隔没有物理依据。

正确写法是**串行等待**:发一个 → 等响应 → 再发下一个。

错误码区分该重试还是该改参数

失败响应的 `code` 字段告诉你该怎么办:

• `bad_request` — 参数不合法 → **不要重试**,改参数
• `not_ready` — 界面或服务尚未就绪 → 稍等再试
• `timeout` — 超时 → 可重试一次
• `busy` — 操作积压 → 等一会儿再发
• `unauthorized` — 令牌不匹配 → 检查 token
• `io` — 读写失败 → 重连

**`bad_request` 重复发送必然重复失败**,这是最容易浪费请求的一种。

最轻的一次往返。用来区分「连不上」「连上了但无障碍没开」「一切正常」三种情况。accessibility 为 false 时,除 ping / info / device 外的命令都会失败。

一次拿全:身份、屏幕、电量(百分比/充电/温度/健康度)、亮灭屏、锁屏、音量(5 种流)、亮度、网络、存储、内存,以及本服务自身的运行状态。不需要无障碍权限,所以服务没绑定时也能用它排查。取不到的值返回 null 或 -1,不会编造一个看起来合理的数。

wake唤醒屏幕

findtext按文本找控件 ⭐

融合节点树与 OCR,并把命中点解析成**真正可点击的控件**。

关键坑:显示文字的节点和能点击的节点**通常不是同一个**。文字常在一个不可点击的 TextView 里,真正响应点击的是它的父 LinearLayout。findtext 会对命中点做命中测试,返回这一点之下「最深且最小」的可点击节点。

ocr本地文字识别

在手机本地跑 OCR(ML Kit bundled 版,模型在 APK 内,**不需要 Google Play 服务**,国行无 GMS 也能用)。

用于节点树看不到内容的场景:WebView/H5、游戏、Canvas、自绘控件、图片里的文字。**原生控件场景优先用 find**,快几百倍且带 viewId。

colorat单点取色

取屏幕上某一个像素的颜色。findcolor 的廉价版:取一个点只要一次截图加一次数组索引,而 findcolor 要扫全屏。**适合轮询状态指示灯,不适合定位目标。**

findmulti多点找色(锚点+偏移)

**单个颜色在真实屏幕上几乎没有辨识度** —— 任何一个色调都有成千上万像素命中,所以单点找色只能告诉你"这个颜色在哪",不能告诉你"那个东西在哪"。

多点找色用**一个锚点色 + 若干固定偏移点**来描述目标:必须**锚点命中,且每个偏移点也各自命中自己的颜色**,才算一处匹配。这样才能在几百个图标里锁定特定那一个。

`points` 是 `[dx, dy, 颜色]` 的数组,坐标**相对锚点**。

**采样要点**:
• 锚点选**稀有、稳定**的像素(纯色背景块最差,满屏都是)
• 偏移点选**纹理丰富**的位置 —— 边缘、文字、图标细节
• 偏移量**越大越精确**,但也越不耐缩放
• 3–6 个偏移点通常就够,超过 48 会被拒

响应里的 `anchorsTried` 能帮你判断锚点选得好不好:**这个数越大,说明锚点色越普通**,匹配会越慢。
参数
anchor锚点颜色 #RRGGBB
points[[dx,dy,"#RRGGBB"], ...] 相对锚点的偏移
tolerance每个通道的容差 0–255,默认 16
region限定搜索范围
max最多返回几处,默认 20

findcolor单点找色(按簇返回)

按颜色查找,返回**按像素数排序的聚类区域**,而不是一堆原始像素点。用于节点树看不到内容、但颜色稳定的目标:徽标、进度条、游戏元素。region 能显著提速。
参数

region限定搜索范围

findimage找图(模板匹配)

朴素全分辨率匹配是 O(宽×高×模板面积)——1080×2400 配 100×100 模板约 2.2×10¹⁰ 次比较,要几十秒。这里先把图和模板降到模板长边约 28px 做穷举粗筛,再对前几个候选在原分辨率上小范围精修,因此能在百毫秒级返回。

**缩小 region 是最有效的提速手段。**

waitstable等待界面稳定

连续 N 帧界面指纹相同即认为稳定,比固定 sleep 可靠得多。**会如实报告是否真的稳定了**,所以调用方能区分「已就绪」和「到点了还在变」。

操作屏幕全部默认拟人——手指不可能每次都落在同一个像素上

tap点击(拟人)

落点带高斯散点(σ≈5.5px)、亚像素级微滑、52–139ms 随机按压时长。

**这不是可选项**:human:false 只是留给 A/B 对照的开关,正常使用不应打开。
参数
x / y全屏截图像素坐标
retry被取消时重试 1–5 次,默认 1
minIntervalMs两次点击最小间隔,默认 110ms;设 0 关闭
human默认 true。false 仅用于对照

doubletap双击(拟人)

两次接触的**间隔(88–209ms)和第二次落点都随机**。

实现细节:两次接触放在**同一条 GestureDescription 的两个 stroke** 里,而不是发两次请求——框架正是靠「同一输入序列内的两次接触」识别双击的,分两次往返反而不成立。

longpress长按(拟人)

按住期间**分 3 段微动**——真人手指不会完全静止。原来的实现是一根静止的直线,特征明显。
参数
holdMs按住时长,300–5000ms,默认 650
retry被取消时重试次数

swipe滑动(到达后停留再抬手)

二次贝塞尔弧线(控制点随机、朝随机侧弯曲约 ±2.2% 弦长)、沿法线叠加的生理性震颤(两端收敛为 0),速度剖面为**加速 → 匀速 → 减速 → 到达后停留约 200ms 再抬手**。

**为什么要有那个停留**:系统在手指离开后按**抬手瞬间的速度**决定要不要继续惯性滚动。末尾速度快就会"甩"出去、落点超出坐标;速度接近 0 才会正好停在目标。

只靠减速曲线做不到这件事:300ms 内既要走完 1000px、又要在最后100ms 爬行,数学上不可能。**停留 200ms 绕开了这道算术** —— 最后那段采样点几乎重合,速度必然是 0,无论滑得多快。

这也正是真人的做法:快速划过去,**停住**,再抬手。停留只有 200ms,不增加可见的耗时。

**实践建议**:
• 需要**落在指定位置** → 用 600–1200ms
• 需要**快速翻页** → 用 200–350ms,现在同样能刹住
• 要**读完整列表** → 用 `sweep`,它自己处理滚动
参数
durationMs60–4000,默认 320。末尾另有约 200ms 停留
human默认 true。false 为机械直线,仅用于对照
tracetrue 时返回 [x,y,timeMs] 采样点,用于画速度曲线

swipemeasure滑动并测量真实位移

滑动,**并告诉你内容实际滚了多远**。

`swipe` 返回 `completed:true` 只说明手势被系统接受了,**完全不代表内容滚动了相应的距离** —— 列表到边界就不再跟手、惯性会让它继续走、页面也可能根本不滚。想知道实情只能量。

做法是滑动前后各截一屏,用归一化互相关找垂直偏移。

**读法**:
• `fingerDistance` 手指走了多远
• `contentShift` 内容实际滚了多少(**-1 表示无法测量**,不是 0)
• `efficiency` = 位移 ÷ 手指距离。**大于 1 说明触发了惯性**
• `matchScore` 匹配相关系数,偏低说明两次截图没对齐(页面变了)
参数
durationMs滑动时长,同上
settleMs滑动后等待多久再截图,默认 800。惯性大的要留足

flick惯性甩动

短而快的滑动,让内容带着惯性继续滚。

**和 swipe 是两种操作**:同样距离慢慢拖是拖拽(内容精确跟随手指),快速甩是抛出(内容继续滚一段),应用对两者的响应确实不同。

pinch双指缩放

两根手指放在**同一条 GestureDescription** 里,所以是同时落下——框架正是靠这个区分「捏合」和「两次独立滑动」。

endSpread 大于 startSpread 是放大,反之缩小。地图、图片查看器、部分游戏没有替代方案。

scroll按容器滚动一屏

找到第 index 个可滚动容器,对它下发 ACTION_SCROLL_FORWARD / BACKWARD。

比「盲滑屏幕」可靠:手势锚定在容器自身边界内,不会误触到浮动按钮或底部导航栏。响应会回传被滚动的容器信息。
参数
directionforward(默认)/ backward
index第几个可滚动容器,默认 0

key系统按键(8 个)

全局系统动作。响应会回传中文名 label,便于日志和展示。

• `BACK` — 返回
• `HOME` — 回到桌面
• `RECENTS` / `APPSWITCH` — 最近任务
• `NOTIFICATIONS` — 下拉通知栏
• `QUICK_SETTINGS` — 快捷设置面板
• `POWER` — 电源菜单
• `LOCK` — 锁屏
• `SCREENSHOT` — 截屏

⚠️ 这里只有**全局动作**,没有 ENTER / 退格——无障碍服务注入不了按键事件。
需要提交输入用 `send`,需要回删用 `delete`。

输入文字不依赖输入法,也不需要剪贴板中转

text向焦点输入框写文本

走 ACTION_SET_TEXT,所以**中文和 emoji 直接可用,不需要输入法,也不走剪贴板**——这正是 adb 方案要额外跑 scrcpy 才能做到的事。

typing:"natural" 会逐字符提交并插入随机间隔。**整段文字在一帧里出现本身就是个信号**,没有人类是那样打字的。代价是慢,只在输入框会观察输入时序时才值得。
参数
text要写入的文本
modereplace(默认)/ append / clear
typinginstant(默认)/ natural

send提交输入(发送 / 搜索 / 完成)

让输入法执行它自己的编辑器动作:聊天框里是「发送」,搜索框里是「搜索」,表单里是「完成」——和你按键盘右下角那个键**是同一个动作**,所以应用对两者的处理完全一致。

⚠️ 这**不是**合成的 Enter 按键。无障碍服务根本无法注入按键事件(那需要 INJECT_EVENTS,只有 shell/系统权限才有),所以只能走输入法这条路。

字段若返回 sent:false,说明它没有声明编辑器动作,此时改用点击发送按钮。

delete回删(退格)

从焦点输入框末尾删除 N 个字符,默认 1。

⚠️ **实现方式的诚实说明**:无障碍没有任何「发送退格键」的动作(同样要 INJECT_EVENTS)。这里的做法是读出当前文本、写回去掉末尾的内容。

**内容上完全等价**,区别在于它是一次原子写入——如果某个输入框会检查按键节奏,是能看出差别的。这是免 root 路线的硬限制,不是实现疏漏。
参数
count删除字符数,1–500,默认 1

clear清空输入框

把焦点输入框清空,返回清空前的内容长度。

比 text 的 mode:"clear" 更直观,单独成一个命令是因为「清空重填」是很常见的一步,值得少写一个参数。

clipboard剪贴板读 / 写 / 粘贴

get 读取、set 写入、paste 注入到当前焦点输入框。

**paste 是救命路径**:某些输入框拒绝 ACTION_SET_TEXT(只认真实输入事件),此时只能先把文本写进剪贴板再粘贴。

应用与系统启动、跳转、结束,以及音量亮度

launch启动应用

按包名启动。需要先知道包名,可以用 apps 查。

deeplink打开 URI(直达页面)

直达某个 App 的具体页面,省掉「启动 → 再点进去」的整段流程。也绕开了「应用打开后停在开屏页或更新提示,模型找不到入口」这类常见失败。

apps已安装应用列表

返回有启动入口的应用(标签 + 包名),可按名称或包名过滤。默认不含系统预装应用。

stopapp结束后台应用

用 killBackgroundProcesses,**这是无 root 情况下能拿到的最强手段**:

它只回收**已在后台**的进程,前台应用不受影响。返回里的 stillRunning 和 note 会如实说明这一点,而不是假装它是 force-stop——真正的前台强停需要 shell 权限。

volume调节音量

走 AudioManager 而不是合成按键事件——**息屏时也能用**,而且不会把焦点抢给别的应用。
参数
streammusic / ring / alarm / notification / voice
actionup / down / mute / unmute / set

brightness调节亮度

需要 **WRITE_SETTINGS 特殊权限**——这个权限**不能通过运行时对话框授予**,必须去「设置 → 应用 → 本 App → 修改系统设置」手动打开。先查 device 返回的 brightness.writable 可以避免无谓失败。

写入时会**同时把亮度模式置为手动**,否则自动亮度机型会立刻覆盖回去。

概念与约定理解这几条能少踩很多坑

坐标约定一切坐标都是全屏截图像素

原点是屏幕左上角,尺寸与截图一致(含导航栏)。

⚠️ 别用 Android 的 resources.displayMetrics——那是「应用可用区域」,在手势导航机型上会少掉导航栏高度(实测 2261 vs 2400)。据此换算会让坐标整体偏移。

截图有缩放时,换算规则:
触摸坐标 = 图像坐标 ÷ scale + region 左上角

两个独立的授权常驻通知 ≠ 无障碍

**常驻通知(前台服务)**:让进程活着,端口继续监听。掉了的表现是「手机从电脑视野里消失」。

**无障碍服务**:允许读界面、截图、注入手势。掉了的表现是「端口还在,但所有操作类命令失败」。

这两个是独立状态,排查时先看掉的是哪一个。

分层选择策略按成本递进,别一上来就烧算力

找目标时按这个顺序,绝大多数情况在第一层就解决了:

1. find 控件树 —— 毫秒级,覆盖原生控件(大多数界面)
2. findtext + OCR —— 数百毫秒,覆盖 WebView、游戏、图片文字
3. findcolor / findimage —— 百毫秒级,无文字但颜色图形稳定
4. observe 交给视觉模型 —— 秒级 + token,前三层都失败时兜底

安全边界免 root 的固有天花板

dispatchGesture 注入的事件由系统统一生成,**压力(getPressure)、接触面积(getSize)、来源设备 id(getDeviceId)无法自定义**。这三项在应用层都是可读的公开 API,属于免 root 路线的硬上限;要覆盖它们只有 sendevent 直接写 /dev/input/eventX,那需要 root。

好消息:InputEvent.isTainted() 是 @hide 的内部标志,普通 App 读不到。

访问令牌可选的端口认证

App 首页「访问令牌」区块控制端口是否要求认证。

• **关闭**(默认)—— 同一局域网内任意设备都能连,**调用不用带令牌**
• **开启** —— 每次调用都必须带 `token`,否则返回 `code:"unauthorized"`

几点设计取舍:
• 令牌与开关**分开存**,关掉保护不会丢密钥
• **重启保持** —— App 重启、手机重启都不变,只有人工点击才会更换
• **更换有二次确认** —— 因为它会让所有正在用旧令牌的脚本和插件**立刻失效**
• 首次启动**自动生成**一个 16 位密钥,但**不会自动开启**保护
• 开关或更换会**重启控制服务**(令牌在服务启动时读一次,换来请求热路径
上不必每次查偏好设置)
